System Architecture

Seven stages — from raw PDF to grounded, streamed answer. Click any stage to explore.

Core Stages

Chunking + Embedding

  • ~400-token sliding window, 60-token overlap
  • Nearest heading stored as section label per chunk
  • MiniLM-L6-v2 → 384-dim L2-normalised embeddings (inner product = cosine)
  • Multi-doc: vstack new embeddings onto existing, full FAISS rebuild

Retrieval + Intent

  • FAISS IndexFlatIP top-k search (k=5 default, configurable 1–20)
  • Zero-shot intent: cosine sim vs 5 description embeddings — no LLM call
  • Index cached in-memory per session; loaded from S3 on first query only
  • Secondary intents logged to MLflow for offline analysis

Prompt Routing + A/B

  • 5 intents × 2 variants = 10 prompt templates
  • ε-greedy selector (10% explore) reads MLflow latency to pick winner
  • v1: detailed prose · v2: structured concise output
  • 1200-word context budget enforced before LLM call

Key Design Decisions

Stateless API via S3

Session state lives entirely in S3 as status.json. Any API replica can serve any request without shared memory — prerequisite for horizontal scaling on Render.

One Model, Three Jobs

MiniLM-L6-v2 loaded once, reused for chunk embedding, query embedding, and zero-shot intent classification. One ~90 MB load serves the full query path — no extra inference cost for intent.

Merge-on-Upload Index

Multi-doc sessions rebuild FAISS by loading existing S3 embeddings and vstacking new ones. IndexFlatIP doesn't support incremental add with persistence — full rebuild is correct.
